# Version 3.85 - Best Practice: Server-Side Search + Pagination untuk Picker Produk (Frontend)

## 1. Problem / Opportunity

*   **Context:** Search produk di iOS "Catat Penjualan" → "Tambah Produk" tidak menemukan produk di luar 500 size pertama. Backend quick fix v3.85 (abaikan limit) sudah di-deploy tetapi berisiko payload besar jika katalog ribuan size.
*   **Objective:** Solusi frontend terpadu dengan backend v3.86: `ProductPickerSheet` kirim parameter `search` ke backend dengan debounce, atau `loadSizes()` pakai pagination loop. Hasil search dari server, tidak dari memori lokal 500 size pertama.
*   **Scope:** Frontend iOS SwiftUI only (backend di `backend/doc/versions/v3.86.md`).

## 2. User Flow & UX Specifications

*   **Entry Point:** Catat Penjualan → Tambah Produk → search field "Cari produk / SKU...".
*   **UI Components:** Search field tetap. Saat user mengetik, tampilkan indikator loading ringan, hasil dari backend.
*   **Validation Rules (`canSave`):** Tidak ada perubahan.
*   **State & Progressive Disclosure:**
    *   Debounce 300–400ms saat mengetik untuk mencegah request terlalu sering.
    *   Jika search kosong, tampilkan daftar default (paginasi atau semua).
    *   Jika tidak ada hasil, tampilkan "Tidak ada hasil pencarian."

## 3. Database Schema Changes (FastAPI / SQLAlchemy)

*   **Tidak ada.** Frontend-only (backend di v3.86).

## 4. API Contract (FastAPI)

*   **Endpoint yang dipakai:** `GET /product-sizes?search=...&page=...&limit=...` (backend v3.86).
*   **APIService.swift:** Tambah overload `getAllProductSizes(page:limit:search:)` yang forwarding parameter `search` ke backend.
*   **Request/Response Body:** Tidak ada perubahan skema. Hanya query parameter `search` yang dikirim.

## 5. Frontend Changes (SwiftUI)

*   **File yang diubah:** `TambahPenjualanSheet.swift` (`TambahPenjualanSheet` + `ProductPickerSheet`).
*   **Opsi A (Disarankan — Server-Side Search):**
    *   `ProductPickerSheet.searchText` → `onChange` dengan debounce 300–400ms → panggil `api.getAllProductSizes(page: 1, limit: 50, search: teks)`.
    *   Simpan hasil ke `products` state, tampilkan dalam list grup per SKU.
    *   Tidak perlu memuat semua 500+ size di awal sheet dibuka.
*   **Opsi B (Pagination Loop):**
    *   `TambahPenjualanSheet.loadSizes()` pakai loop `while true` dengan `getAllProductSizes(page:limit:)` hingga `nextPage == nil` (mirip `ProdukListView.fetchAllSizesBulk()`).
    *   Search tetap lokal di memori, tapi semua size sudah dimuat.
    *   Risiko memori jika katalog ribuan size.
*   **Backward compatibility:** Backend v3.86 support `?all=true` untuk frontend versi lama yang masih hardcode limit=500 tanpa pagination.

## 5.5. QR Product Cache Miss Handling

*   **Masalah:** Jika frontend menggunakan Opsi A (server-side search, tidak memuat semua size di awal), `QRProductCache.shared.lookup(id)` dapat mengalami **miss** saat QR scan mencari size yang belum dicache.
*   **Handling:** Biarkan `lookup(id)` dapat miss. Saat cache kosong, fallback ke `api.getProductSizeById(id:)` untuk mengambil detail dari server, lalu upsert ke cache agar scan berikutnya langsung hit.
*   **Kode referensi existing:** `QRProductCache.refreshOne(id:api:)` di `QRProductCache.swift` baris 185-190 dan `TambahPenjualanSheet.refreshScannedPrice()` baris 513-535.
*   **Implementasi di QRScannerSheet:** Panggil `lookup(id)` terlebih dahulu; jika `nil`, panggil `refreshOne(id:api:)` atau `getProductSizeById(id:)` sebagai fallback.

## 6. Verification & Test Plan

*   **Smoke Test:** Xcode build berhasil, sheet "Tambah Produk" dapat dibuka tanpa crash.
*   **Sanity Test Scenarios:**
    1.  Buka "Tambah Produk", ketik "kemeja" → hasil search muncul dari server (bukan hanya dari 500 size pertama).
    2.  Kosongkan search → kembali ke daftar default.
    3.  Ketik cepat → debounce mencegah request berlebihan.
    4.  Ketik SKU yang ada di luar 500 pertama → produk tersebut muncul dalam hasil.
*   **Sanity Test Scenarios (QR Cache Miss):**
    1.  Scan QR produk yang belum ada di cache → `lookup(id)` mengembalikan `nil` → sistem fallback ke `api.getProductSizeById(id:)` → detail produk muncul dan di-upsert ke cache.
    2.  Scan QR produk yang sama kedua kalinya → `lookup(id)` hit dari cache, tidak perlu panggil API lagi.
*   **Regression:** Endpoint `GET /products` (ProdukListView) tidak terpengaruh. QR scan, generator QR, resep produksi tetap normal.
