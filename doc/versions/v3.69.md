# Version 3.69 — Slim Scan-Resolve Endpoint + QR v2 Embedded (Fullstack Follow-up)

**Status:** PLANNED — belum diimplementasikan (follow-up dari v3.68)
**Date planned:** 2026-10-08
**Changed by:** Fullstack
**Prasyarat:** v3.68 (`doc/versions/v3.68.md`) sudah implemented — cache lokal + parser `oura:`/`oura2:` sudah ada.

## 1. Problem / Opportunity
*   **Context:** v3.68 menghilangkan RTT per-scan via cache, tapi preload masih memakai DTO penuh `ProductSizeDetail` (termasuk `latest_hpp_breakdown`, `images`, manual HPP) dan revalidasi masih N× `GET /product-sizes/{id}`. Untuk 1000+ varian / koneksi pasar yang buruk, ini masih berat.
*   **Objective:** Satu round-trip ringan untuk resolve/revalidasi banyak id + QR v2 yang bisa render instan tanpa cache sama sekali.

## 2. User Flow & UX Specifications
*   **Entry Point:** Sama seperti v3.68. Tidak ada layar baru.
*   **Perubahan flow:** `QRProductCache.revalidate(ids:)` memanggil 1× batch endpoint (di bawah) alih-alih N× paralel. Generator QR mencetak format `oura2:<uuid>:<priceCents>:<shortName>`; scanner merender nama+harga dari payload dalam <5ms meski cache kosong, lalu verifikasi slim di background.
*   **Validation (`canSave`):** Sama seperti v3.68. Payload embedded tidak pernah dipercaya untuk stok — stok selalu dari server (cache/batch).
*   **State:** Tambah badge "offline-embedded" kecil saat item dirender murni dari QR sebelum verifikasi.

## 3. Database Schema Changes (FastAPI / SQLAlchemy)
*   Nihil (read-only endpoint, manfaatkan indeks existing di `product_size.id`). Jika `EXPLAIN` menunjukkan seq-scan, tambah indeks `ix_product_size_id` — verifikasi saat implementasi.

## 4. API Contract (FastAPI)
*   **Endpoints (baru):**
    *   `GET /product-sizes/scan-resolve?ids={uuid,uuid,...}` (max 50 id)
        *   **Response:** array slim `[{id, product_name, size_label, fabric_variant_name, current_stock_qty, selling_price, is_archived}]` — tanpa HPP/images/manual-HPP.
        *   **Errors:** `422` jika >50 id atau UUID invalid; id yang tidak ditemukan di-skip (tidak 404 seluruh batch) + sertakan `missing_ids: [...]`.
    *   `GET /product-sizes/slim?page=&limit=` (opsional, untuk preload 1000+ varian) — payload sama seperti di atas dalam envelope paginasi existing.
*   Catatan backend: query tunggal `WHERE id IN (...)`, tanpa JOIN HPP/images; pertimbangkan `Cache-Control: private, max-age=15` karena stok bergerak cepat.

## 5. Frontend Changes (SwiftUI)
*   `QRProductCache`: tambah `revalidateBatch(api:ids:)` → panggil endpoint baru, fallback ke N× `getProductSizeById` jika backend belum deploy (feature-flag `supportsBatchResolve` via again-try).
*   `QRGeneratorView`: opsi "Label v2 (dengan harga)" → encode `oura2:`; pertahankan default `oura:` agar printer lama tetap jalan.
*   `QRScannerSheet.parseQR`: pecah `oura2` 3 segmen (uuid, price, shortName).

## 6. Verification & Test Plan
*   **Smoke:** Build + batch resolve 20 id dalam 1 call (cek log 1 request); fallback N× saat endpoint 404.
*   **Sanity:** (1) preload 1000 varian slim <1.5s di LTE; (2) scan `oura2` dengan cache dikosongkan → nama+harga langsung tampil; (3) id hilang → `missing_ids` tampil sebagai error card; (4) regresi v3.68 (5 skenario) tetap hijau.
