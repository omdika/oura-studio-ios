# v2.4 — Live Backend Integration + API Format Fixes
**Date:** 2026-08-07  
**Changed by:** Frontend

---

## Summary

First session wiring the iOS app to the live FastAPI backend on Google Cloud Run. Every major screen was broken due to mismatches between frontend Swift model structs and actual backend JSON format. This version documents all discovered format differences, the client-side enrichment pattern used to bridge them, and three additional UX fixes uncovered during testing.

**Backend URL:** `https://oura-backend-jkt-763614853578.asia-southeast2.run.app/api/v1`

---

## 1. Root Cause Pattern

All decode errors shared the same cause: frontend `Codable` structs expected enriched/nested fields (`product_name`, `size_label`, `fabrics[]`, etc.) but backend returns flat IDs. `JSONDecoder` throws `keyNotFound` on any missing non-optional field → wrapped as `APIError.decodingError` → silent failure (via `try? await`) returns `nil` → UI shows empty state.

**Fix pattern used throughout:** add a `Backend*` struct matching actual response, decode into it, then enrich client-side by fetching related entities and building lookup dictionaries.

## 2. Backend Format Mismatches Fixed

### 2.1 GET /pattern-specs — `BackendPatternSpec`

**Problem:** frontend decoded as `PatternSpec` which expects `product_name`, `size_label`, `fabrics[]` array — none of these exist in backend response.

**Actual backend format:**
```json
{
  "id": "...",
  "product_size_id": "...",
  "fabric_material_id": "...",
  "cut_width_cm": 21.0,
  "cut_height_cm": 90.0,
  "rotation_allowed": true,
  "est_labor_minutes": 12.0,
  "is_active": true,
  "effective_from": "...",
  "effective_to": null,
  "components": [{ "id": "...", "material_id": "...", "qty_per_unit": 1.0 }]
}
```

**Fix:** Added `BackendPatternSpec` + `BackendPatternComponent` structs. `getPatternSpecs()` now decodes as `[BackendPatternSpec]` then calls `enrichPatternSpecs()` which fetches all products + their sizes in parallel via `fetchSizeToProductMap()` to resolve names.

**Files:** `Models/PatternSpecModels.swift`, `APIService.swift`

---

### 2.2 GET /products/{sku}/sizes — `ProductSizeBasic`

**Problem:** frontend decoded as `[ProductSizeDetail]` which has non-optional `product_sku`, `product_name`, `production_stock_qty`, `manual_stock_qty` — none exist in list response.

**Actual backend format:**
```json
{
  "id": "...",
  "product_id": "...",
  "size_label": "L",
  "fabric_variant_name": "Waffle Merah",
  "reorder_min_qty": null,
  "selling_price": null,
  "is_archived": false,
  "current_stock_qty": 3
}
```

**Fix:** Added `ProductSizeBasic` struct matching actual flat format. Added two helpers to `APIService`:
- `sizeDetailFromBasic(_:sku:productName:)` — converts `ProductSizeBasic` to `ProductSizeDetail` (fills `productionStockQty: 0`, `manualStockQty: 0` since list endpoint doesn't return breakdown)
- `resolveProductName(sku:)` — fetches `/products`, finds by SKU, returns name

Updated: `getProductSizes`, `createProductSize`, `patchProductSize`, `adjustStock`, `addStockFromBahan`, `addStockManual`, `getAllProductSizes`.

**Files:** `Models/ProductModels.swift`, `APIService.swift`

---

### 2.3 `fetchSizeToProductMap()` — Shared Helper

**Problem:** Both pattern spec enrichment and production batch enrichment needed product+size lookups. Previously each was doing independent fetches.

**Fix:** Extracted `private func fetchSizeToProductMap() async throws -> [UUID: (product: Product, size: ProductSizeBasic)]`. Fetches all products, then fetches all their sizes in parallel via `withTaskGroup`. Returns a lookup from `size.id → (product, size)`. Used by `enrichPatternSpecs`, `suggestLayouts`, `enrichProductionBatches`.

### 2.4 POST /cutting-optimizer/suggest — `BackendSuggestOptimizerResponse`

**Problem:** frontend decoded as `SuggestOptimizerResponse` which expects `OptimizerLayout` with non-optional `id`, `totalQty`, `productName`, `sizeLabel` — none exist in backend response.

**Actual backend format:**
```json
{
  "layouts": [{
    "strategy": "max_qty",
    "waste_pct": 5.2,
    "items": [{ "product_size_id": "...", "pattern_spec_id": "...", "orientation": "normal",
                "qty_suggested": 8, "fabric_length_used_cm": 80.0, "cost_per_piece": 5000.0 }]
  }]
}
```

**Fix:** Added `BackendSuggestOptimizerResponse`, `BackendOptimizerLayout`, `BackendOptimizerLayoutItem`. `suggestLayouts()` decodes as backend type, then enriches items with product/size names via `fetchSizeToProductMap()`, generates UUIDs client-side.

**Files:** `Models/OptimizerModels.swift`, `APIService.swift`

### 2.5 POST /cutting-optimizer/layouts — `BackendCreateLayoutResponse`

**Problem:** frontend decoded backend response as `CuttingLayout` (full object), but backend only returns the new ID.

**Actual backend format:**
```json
{ "cutting_layout_id": "..." }
```

**Fix:** Added `BackendCreateLayoutResponse`. `createLayout()` decodes into it and returns a stub `CuttingLayout` with the ID filled in.

### 2.6 GET /production-batches — `BackendProductionBatch`

**Problem:** frontend decoded as `[ProductionBatch]` whose `ProductionBatchItem` has non-optional `production_batch_id`, `product_name`, `size_label` — none exist in backend item response.

**Additional finding:** `hpp_*` fields are all `0.0` in draft status. Backend computes HPP only at confirmation. Backend DOES return `fabric_cost_per_piece` even in draft.

**Actual backend item format:**
```json
{
  "id": "...", "product_size_id": "...", "pattern_spec_id": "...",
  "qty_actual": 9, "cutting_layout_item_id": "...", "material_purchase_id": "...",
  "fabric_cost_per_piece": 5000.0, "fabric_length_per_unit_cm": 11.1,
  "hpp_fabric": 0.0, "hpp_pooled_material": 0.0, "hpp_hardware": 0.0,
  "hpp_labor": 0.0, "hpp_overhead": 0.0, "hpp_total": 0.0
}
```

**Fix:** Added `BackendProductionBatch`, `BackendProductionBatchItem` (includes `fabricCostPerPiece`). `enrichProductionBatches()` uses `fetchSizeToProductMap()` for names. When `hpp_total == 0`, uses `fabricCostPerPiece` as `hppFabric` so draft items show a partial estimate instead of Rp0.

**UI change:** `BatchItemRow` now shows `~kain Rp.../pcs` (tilde prefix = estimate) when `hppTotal == 0` and `hppFabric > 0`, and `HPP Rp.../pcs` when `hppTotal > 0` (confirmed batch).

**Files:** `Models/ProductionModels.swift`, `APIService.swift`, `Screens/Produksi/ProduksiBatch/ProduksiBatchView.swift`

### 2.7 POST /pattern-specs — `BackendCreatePatternSpecRequest`

**Problem:** frontend sent `fabrics: [{material_id, cut_length_cm, cut_width_cm, rotation_allowed}]` as an array. Backend expects flat fields at root level, and uses `cut_height_cm` (not `cut_length_cm`) for the long dimension.

**Backend error response:**
```json
{"detail": [{"type": "missing", "loc": ["body", "fabric_material_id"], "msg": "Field required"}, ...]}
```

**Correct backend format:**
```json
{
  "product_size_id": "...",
  "fabric_material_id": "...",
  "cut_width_cm": 20,
  "cut_height_cm": 100,
  "rotation_allowed": true,
  "est_labor_minutes": 22,
  "components": [{ "material_id": "...", "qty_per_unit": 1.0 }]
}
```

**Additional validation:** `est_labor_minutes` must be `> 0` (backend returns 422 if 0).

**Fix:** Added `BackendCreatePatternSpecRequest` struct with flat fields. `createOrUpdatePatternSpec()` maps `fabrics[0]` to these flat fields (backend is 1-fabric-per-spec). `canSave` in `TambahResepSheet` now requires `(laborMinutes ?? 0) > 0`.

**Files:** `Models/PatternSpecModels.swift`, `APIService.swift`, `Screens/Produksi/Resep/TambahResepSheet.swift`

---

### 2.8 PATCH /products/{sku} — Archive via PATCH, not DELETE

**Problem:** `archiveProduct` was calling `DELETE /products/{sku}`. Backend's DELETE hard-deletes the product and cascades to sizes and their pattern specs — all resep disappeared on archive.

**Backend behavior discovered:**
- `DELETE /products/{sku}` → hard delete + cascade (destroys pattern spec history)
- `PATCH /products/{sku}` with `{ "name": "...", "is_archived": true }` → soft archive ✅
- `PATCH /products/{sku}/sizes/{sizeId}` with `{ "is_archived": true }` → soft archive ✅ (no name required)
- Unarchiving via PATCH with `is_archived: false` is NOT supported (one-way soft delete)
- `POST /products/{sku}/archive` does not exist (404)

**Fix:** 
- Added `ArchiveProductRequest` struct (includes `name` since backend requires it)
- `archiveProduct(sku:currentName:)` now calls PATCH instead of DELETE
- `archiveProductSize(sku:sizeId:)` now calls PATCH with `PatchProductSizeRequest(isArchived: true)` instead of DELETE
- `PatchProductSizeRequest` gained optional `isArchived: Bool?` field
- `archiveProduct` signature changed to include `currentName: String` parameter
- Call site in `ProdukDetailView.archiveProduct()` updated to pass `product.name`

**Files:** `Models/ProductModels.swift`, `APIService.swift`, `Screens/Produk/ProdukDetailView.swift`

## 3. UX Fixes (Discovered During Live Testing)

### 3.1 SKU Auto-Generator — Per-Word Prefix

**Problem:** `autoSKU(from:)` took the first 8 characters of the full alphanumeric name. "Scrunchie Waffle" → "SCRUNCHI", same as "Scrunchie Satin" → "SCRUNCHI". All scrunchie variants collided.

**Fix:** Take up to 3 characters from each word, concatenate, cap at 8.

```
"Scrunchie Waffle Merah" → "SCR"+"WAF"+"MER" = "SCRWAFME"
"Scrunchie Satin"        → "SCR"+"SAT"       = "SCRSAT"
"Ikat Rambut"            → "IKA"+"RAM"       = "IKARAM"
```

**File:** `Screens/Produksi/Resep/TambahResepSheet.swift` (`TambahProdukCepatSheet.autoSKU`)

## 4. API Behavior Notes for Backend Reference

These were discovered empirically during frontend integration testing:

| Endpoint | Finding |
|---|---|
| `POST /pattern-specs` | Requires flat fields, NOT `fabrics[]` array. `est_labor_minutes` must be > 0. `cut_height_cm` is the long dimension (UI calls it "Panjang"). |
| `POST /cutting-optimizer/layouts` | Returns only `{ cutting_layout_id }`, not a full layout object. |
| `GET /production-batches` | Items have `hpp_*: 0.0` in draft status — HPP computed at confirmation only. `fabric_cost_per_piece` is available in draft. |
| `PATCH /products/{sku}` | Requires `name` field even when only archiving. `is_archived: false` is silently ignored (can't unarchive). |
| `PATCH /products/{sku}/sizes/{id}` | Accepts `is_archived` without requiring `selling_price` or `reorder_min_qty`. |
| `DELETE /products/{sku}` | Hard delete with cascade to sizes and pattern_specs — use PATCH with `is_archived: true` instead for soft archive. |
