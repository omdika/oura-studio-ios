# Version 3.83 - Sinkronisasi Total Pendapatan Penjualan vs Laporan Penjualan

## 1. Problem / Opportunity

*   **Context:** Halaman **Penjualan** (`PenjualanListView`) dan halaman **Laporan Penjualan** (`SalesReportDetailView`) menampilkan total pendapatan yang berbeda meskipun rentang tanggal sama (contoh kasus: Rp1.300.000 / 50 trx vs Rp6.662.834 / 261 trx).
*   **Root cause:** Endpoint `GET /sales-orders` di backend `sales.py` `list_sales_orders` pakai `limit=50` default. Halaman Penjualan hanya menerima 50 order terbaru dan menghitung total-nya sendiri di frontend, sedangkan Laporan pakai `GET /reports/sales` yang `.all()` tanpa limit dan agregasi di server.
*   **Objective:** Agar total pendapatan, total transaksi, dan total pcs terjual di halaman Penjualan konsisten dengan Laporan Penjualan untuk rentang tanggal yang sama, tanpa menambah endpoint baru.

## 2. User Flow & UX Specifications

*   **Entry Point:** Tab Penjualan → `PenjualanListView` (tidak ada perubahan UI visual).
*   **UI Components:** Tidak ada komponen baru. Summary tile (Pendapatan, Terjual, Transaksi) tetap ditampilkan seperti sekarang.
*   **Validation Rules (`canSave`):** Tidak berlaku (read-only).
*   **State & Progressive Disclosure:** Tidak ada perubahan state tambahan di UI.

## 3. Database Schema Changes (FastAPI / SQLAlchemy)

*   **Affected Tables:** Tidak ada (nol migrasi, nol kolom baru).
*   **New / Modified Columns:** Tidak ada.

## 4. API Contract (FastAPI)

*   **Endpoints yang diubah:** `GET /sales-orders` (`list_sales_orders` di `backend/app/routers/sales.py`).
*   **Perubahan perilaku:**
    *   Jika parameter `from` dan/atau `to` (daterange) disertakan → abaikan `limit`/`offset` default, gunakan `.all()` sehingga **semua** order dalam periode dikembalikan.
    *   Jika tidak ada parameter tanggal → tetap pakai pagination default (`limit=50`, `offset=0`) agar tidak membebani saat daftar penuh tanpa filter.
    *   Filter `status != "cancelled"` tetap ditangani di frontend (`PenjualanListView.validOrders`), tidak diubah di backend (untuk menjaga konsisten dengan perilaku existing).
*   **Request/Response Body:** Tidak ada perubahan skema `SalesOrderOut`. Hanya logika pengambilan baris yang berubah.
*   **Validation & Errors:** Tidak ada error baru.

## 5. Frontend Changes (SwiftUI)

### 5.1 `Networking/APIService.swift` — `getSalesOrders(from:to:)`
*   **Verifikasi (tidak perlu edit):** Fungsi sudah hanya menambahkan `?from=&to=` saat kedua tanggal diisi, **tidak mengirim `limit`/`offset`**. Tidak perlu perubahan kode.
*   Path: `.../Networking/APIService.swift` baris ~1037–1044.

### 5.2 `Screens/Penjualan/PenjualanListView.swift`
*   **Verifikasi (tidak perlu edit):**
    *   `load()` memanggil `api.getSalesOrders(from: fromDate, to: toDate)` (baris ~268).
    *   `totalRevenue` dihitung dari `validOrders.reduce` + `displayRevenue` (baris ~227–229). Semua order yang diterima dari backend akan terakumulasi.
    *   `totalPcsSold` / `totalTransactions` dihitung dari `orders` yang sama.
*   Setelah backend tidak lagi memotong 50 baris saat daterange aktif, total yang dihitung frontend akan otomatis sama dengan Laporan.

### 5.3 Ringkasan dampak frontend
*   Nol file Swift yang perlu diedit. Perubahan hanya di backend.
*   Setelah deploy backend, hapus cache URLSession jika perlu (cache policy `.useProtocolCachePolicy` sudah ada; data baru akan dimuat ulang saat ganti periode karena `DateRangeField` memicu `load(silent: true)`).

## 6. Verification & Test Plan

*   **Smoke Test:** Build Xcode sukses (`xcodebuild` / simulator). Tab Penjualan dan Tab Laporan bisa dibuka tanpa crash.
*   **Sanity Test Scenarios:**
    1.  Buka halaman Penjualan dengan rentang tanggal (mis. 9 Agu – 7 Nov 2026). Catat total Pendapatan / Transaksi / Pcs.
    2.  Buka halaman Laporan Penjualan dengan rentang tanggal yang **sama**. Total Pendapatan / Transaksi / Pcs harus **sama persis** dengan halaman Penjualan.
    3.  Ubah rentang tanggal di kedua layar (mis. hanya 1 minggu). Kedua layar tetap konsisten.
    4.  Pastikan transaksi dengan status `cancelled` tidak ikut dihitung di kedua layar (Penjualan lewat `validOrders.filter { !$0.isCancelled }`, Laporan lewat backend `status != "cancelled"`).
*   **Backend Test (manual/cURL):** Panggil `GET /sales-orders?from=2026-08-09&to=2026-11-07` → harus mengembalikan lebih dari 50 order (harusnya 261 non-cancelled sesuai data kasus). Tanpa parameter `from`/`to` → harus tetap terbatas 50 order.
*   **Regression:** Pastikan fitur tambah/edit/batal penjualan masih bekerja (endpoint POST/PATCH/DELETE `/sales-orders` tidak tersentuh).

---

Catatan: Alternatif yang dipertimbangkan namun **tidak dipilih** adalah Opsi A (frontend panggil `GET /reports/sales` untuk total terpisah). Dibatalkan karena menambahkan pemanggilan API kedua hanya untuk angka total, sementara pendekatan backend ini menyatukan logika di satu tempat dan lebih ringan untuk client.
